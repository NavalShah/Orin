# ==============================================================================
# 1. PRODUCT SUMMARY AND GOALS
# ==============================================================================
# Orin converts and arranges music between traditions so people who know one
# system can engage with another. Example problem: a person who knows Carnatic
# music (sangeetham) and a person who plays piano cannot easily share material,
# because Carnatic melody is hard to write in staff notation and piano cannot
# play its ornaments.
#
# Orin does three things, as three user-facing parts:
#   A. Chatbot            - talk to Gemini, get music generated by ElevenLabs.
#   B. Notation Studio    - audio or notes in, notation in a chosen genre out.
#   C. Audio Workspace    - FL Studio-style editor to load, arrange and make music.
#
# Core educational idea: the LOSS REPORT. Whenever one tradition's music is
# expressed in another, Orin lists exactly what could not be carried over
# (a gamaka a piano key cannot play, a quarter-tone rounded by 50 cents) and
# Gemini explains why. The gap is a teaching moment, not a bug.
#
# Non-goals:
#   - Claiming support for "everything". Say the architecture is extensible.
#   - Perfect transcription. Transcription is approximate by design; show confidence.
#   - Full polyphonic transcription. v1 handles one melody line (see section 7.4).
#   - Replacing a real DAW. Part C is a lightweight workspace, not a full FL Studio.


# ==============================================================================
# 2. CARRIED-OVER DECISIONS FROM THE EARLIER CHAT
# ==============================================================================
# D1. ElevenLabs CANNOT do audio-to-sheet-music. Scribe is speech-to-text, not notes.
#     Do not build transcription on ElevenLabs.
# D2. ElevenLabs is used for: Music API (text-to-music, incl. mid-track genre
#     transitions), training/example clips per genre, and text-to-speech narration
#     of Gemini explanations.
# D3. Gemini is used for: chat, prompt refinement, and explaining musical elements
#     and loss-report items.
# D4. Transcription uses Basic Pitch (audio -> MIDI) plus a pitch tracker
#     (CREPE or pYIN for monophonic vocals), plus tonic detection.
# D5. Western staff notation is NOT the hub. It is lossy (12 equal pitches, bar
#     lines, no microtones). The hub is a neutral Intermediate Representation.
# D6. Each genre/tradition is ONE adapter file: pitch table + rhythm template +
#     ornament table (+ renderer registrations).
# D7. Every adapter returns a loss report.
# D8. Scope honesty: at most a few traditions fully reviewed for the demo.
# D9. All pitch/mode tables must be reviewed by a practitioner of that tradition
#     before being shown to judges. Mark each table with a review status.
# D10. Prototype status to preserve: 43 offline tests passed; live Gemini and
#      ElevenLabs calls were NOT tested; synthetic singing only; large gamakas
#      (> ~60 cents) split a note; raga table simplified (just-intonation cents,
#      note sets only).
# D11. Offline mode: with no API keys, Gemini and ElevenLabs steps fall back to
#      built-in stand-ins so everything still runs. KEEP THIS.
# D12. Keys live in environment variables only: GEMINI_API_KEY, ELEVENLABS_API_KEY,
#      ELEVENLABS_VOICE_ID (optional), GEMINI_MODEL (optional). Never in git,
#      never in chat, never in the frontend bundle.
# D13. ElevenLabs music generation needs a paid plan; TTS works on lower plans.
#      The app must detect the plan error and degrade gracefully (section 10.9).
# D14. Model names change often. Never hardcode; read from env/config and verify
#      against current docs before the demo.

# 4. MANDATORY REQUIREMENT 1: MUSIC FORMAT REGISTRY
# ==============================================================================
# Goal: a curated, extensible list of music formats (genres/traditions). The app
# converts from one format to another. "Format" here means a musical SYSTEM
# (pitch + rhythm + ornament conventions + notation style), not just a label.
#
# 4.1 Registry entry fields [MUST]
#   id                  stable slug, e.g. "carnatic"
#   display_name        UI label, e.g. "Carnatic (Sangeetham)"
#   aliases             search terms, e.g. ["sangeetham","south indian classical"]
#   family              "indian_classical" | "western_art" | "western_popular" |
#                       "middle_eastern" | "blues_derived" | "other"
#   pitch_system        "12tet" | "just_intonation_srutis" | "maqam_quarter_tones" |
#                       "blues_inflected" | "custom_cents_table"
#   tonic_model         "movable_sa" | "fixed_key_signature" | "movable_root"
#   mode_table          named modes/scales/ragas with allowed pitches in cents
#   rhythm_model        "tala_cycle" | "meter_bars" | "swing_grid" | "free_time"
#   rhythm_templates    list of cycle definitions (see 4.3)
#   ornament_table      named ornaments and how to express/approximate them
#   renderers           which output notations this format can produce
#   input_parsers       which text/note inputs this format can accept
#   monophonic_only     bool (v1: true for all; see 7.4)
#   review_status       "unreviewed" | "self_checked" | "practitioner_reviewed"
#   reviewer_note       free text (who reviewed, what caveats)
#   caveats             shown in UI (e.g. "maqam tuning varies by region/performer")
#
# 4.2 Initial format list
#
#   TIER 1 - REQUIRED FOR DEMO [MUST]
#   ---------------------------------------------------------------------------
#   1. western_classical  "Western (staff notation)"
#        12-TET, bar lines, key signatures. Baseline renderer target.
#   2. carnatic           "Carnatic (Sangeetham)"
#        Movable Sa, swarasthanas (Sa Ri Ga Ma Pa Dha Ni), melakarta/janya ragas,
#        talas (Adi, Rupakam, Misra Chapu, Khanda Chapu, ...), gamakas.
#        Output: sargam text (S R G M P D N with octave marks), optional staff approx.
#   3. western_pop        "Western Pop"
#        12-TET, 4/4 default, major/minor keys, chord-symbol-friendly, syncopation,
#        verse/chorus structure hints. Differs from classical mainly in rhythm
#        feel, typical progressions, and instrumentation idioms.
#   4. rock               "Rock"
#        12-TET, 4/4 (also 6/8, 12/8), pentatonic/blues-scale tendencies, power
#        chords, riff-based. Output: staff + guitar tab (see 4.4).
#
#   TIER 2 - TEACH A DIFFERENT KIND OF LOSS [SHOULD]  (order = cheapest first)
#   ---------------------------------------------------------------------------
#   5. hindustani         "Hindustani"  - reuses swara table; raags, taals, meend.
#   6. arabic_maqam       "Arabic Maqam" - quarter tones (~150 and ~350 cents),
#                         best demo of PITCH loss on a piano.
#   7. blues              "Blues" - blue notes, bends, swing rhythm. Shows loss
#                         that staff notation hides (ambiguous "in-between" third).
#
#   TIER 3 - STRETCH [COULD]
#   ---------------------------------------------------------------------------
#   8. gamelan            Pelog/slendro, non-12-tone, cyclic layering.
#   9. jazz               Only melody line; harmony out of scope for v1.
#
# 4.3 Rhythm template definition [MUST]
#   {
#     "id": "adi_tala",
#     "cycle_beats": 8,
#     "subdivision": 4,                      # pulses per beat (nadai/gati)
#     "structure": ["clap","clap","clap","clap","clap","wave","clap","wave"]   # illustrative
#     "accent_pattern": [1,0,0,0,1,0,1,0],
#     "swing_ratio": null                    # e.g. 2.0 for hard swing (blues/jazz)
#   }
#   Western meters (4/4, 3/4, 6/8, 12/8) use the same shape with a bar as the cycle.
#   Honesty note: tala structure arrays above are illustrative; the real table
#   must be reviewed by a Carnatic practitioner (D9).
#
# 4.4 Output notation styles per format [MUST unless tagged]
#   western_*      : ABC text [MUST], MusicXML [SHOULD], MIDI [MUST], rendered
#                    staff (Verovio SVG) [MUST]
#   carnatic       : sargam text with octave dots and duration marks [MUST],
#                    ornament markings inline [MUST], MIDI approximation [MUST]
#   hindustani     : sargam text with taal markers (sam, khali) [SHOULD]
#   arabic_maqam   : staff with quarter-tone accidentals (half-flat/half-sharp
#                    symbols) [SHOULD]; sargam-like solfege optional [COULD]
#   rock           : staff + 6-string guitar tab [SHOULD]; tab renderer is new work
#   blues          : staff with swing annotation + blue-note markings [SHOULD]
#
# 4.5 UI exposure [MUST]
#   - Dropdowns (Notation Studio) are generated from the registry, grouped by family.
#   - Each entry shows a review-status badge and its caveats on hover/tap.
#   - Adding a format = adding one adapter file + registry entry, with no UI code change.
#
# 4.6 Conversion matrix [MUST]
#   Any input format -> any output format via the IR. N input x M output pairs
#   must work without N*M bespoke code. Test every Tier-1 pair (4x4 = 16) with at
#   least one fixture each, asserting the loss report is non-empty where loss is expected.


# ==============================================================================
# 5. FORMAT ADAPTER SPECIFICATION
# ==============================================================================
# Each adapter module (formats/<id>.py) exposes:
#
#   META: FormatMeta                              # registry fields from 4.1
#   def parse_notes(text|file) -> IR              # notes input -> IR        [MUST]
#   def ir_to_format(ir: IR, opts) -> FormatScore # quantize/snap/drop       [MUST]
#   def render(score: FormatScore, kind) -> bytes|str   # notation output   [MUST]
#   def score_fit(ir: IR) -> float                # 0..1 how well IR fits this format
#                                                 # (feeds style auto-detect)   [SHOULD]
#
# ir_to_format does exactly three things (D6):
#   1. QUANTIZE pitches to the target pitch system (cents -> nearest allowed pitch,
#      constrained by the chosen mode where applicable).
#   2. SNAP rhythm to the target cycle/grid (tala, bar, swing grid).
#   3. DROP or APPROXIMATE what cannot be expressed, and record each one as a
#      LossItem (section 9.3).
#
# Rules:
#   - Adapters never mutate the input IR (return a new object).
#   - Adapters never raise on musical weirdness; they degrade and log loss.
#   - Every approximation > 0 cents is logged (threshold configurable; default 5 cents).
#   - Adapter output includes the options used (mode chosen, tonic, tempo) so the
#     result is reproducible.


# ==============================================================================
# 6. THE INTERMEDIATE REPRESENTATION (IR)
# ==============================================================================
# The IR is Orin's novelty alongside the loss report. It is format-neutral.
# Serialize as JSON; validate with pydantic.
#
# 6.1 Top level
#   IR {
#     version, source { kind: audio|notes, filename, format_hint, detected_format,
#                       detected_format_confidence, duration_s, sample_rate },
#     tonic    { hz, cents_ref_hz, confidence, method },
#     mode     { label, label_system, allowed_pitches_cents[], confidence, candidates[] },
#     tempo    { bpm|null, confidence, free_time: bool },
#     cycle    { length_pulses, subdivision, label|null, confidence, template_id|null },
#     events[] , contour[] , meta { warnings[], processing_log[] }
#   }
#
# 6.2 Note event [MUST]
#   {
#     id, onset_s, offset_s, onset_pulse|null, duration_pulses|null,
#     pitch_cents,                # cents relative to tonic (NOT note names)
#     pitch_cents_median, pitch_cents_min, pitch_cents_max,
#     velocity|loudness_db,
#     voiced_fraction,
#     ornament { kind|null, contour_ref|null, amplitude_cents, rate_hz, shape },
#     confidence                  # 0..1
#   }
#
# 6.3 Contour [MUST for gamaka/meend/bend support]
#   Per-event or global array of {t_s, cents|null, confidence}, sampled at
#   fixed hop (default 10 ms). null = unvoiced. Ornaments are derived FROM this,
#   not stored only as labels, so renderers can approximate differently.
#
# 6.4 Rhythm [MUST]
#   Onsets + cycle length. No bar lines baked in. A renderer may impose bars/tala
#   later. If tempo is unstable, set tempo.free_time = true (e.g. alapana) and
#   renderers output unmeasured notation with a warning.
#
# 6.5 Confidence propagation [MUST]
#   Every stage writes its confidence. Final per-event confidence =
#   product/min policy documented in code. Low-confidence events are rendered
#   visually distinct in the UI (e.g. dimmed) and listed in warnings.
#
# 6.6 Invariants (unit-tested)
#   - events sorted by onset; no overlaps in monophonic mode.
#   - pitch_cents finite; contour timestamps monotonic.
#   - JSON round-trip is lossless.
#   - IR validation errors are surfaced to the user as readable messages.


# ==============================================================================
# 7. MANDATORY REQUIREMENT 2: AUDIO/NOTES -> IR PIPELINE (GRANULAR)
# ==============================================================================
# The app takes BOTH notes and audio files as input, plus a STYLE SELECTOR:
#   - explicit style (choose from registry), or
#   - "Auto-detect" (section 8).
# The prototype pipeline worked on synthetic singing only. The items marked
# [IMPROVE] are the required upgrades over the prototype.
#
# 7.0 Pipeline overview
#   INPUT -> 7.1 ingest -> 7.2 preprocess -> 7.3 stem separation -> 7.4 melody
#   isolation -> 7.5 pitch tracking -> 7.6 voicing cleanup -> 7.7 tonic
#   detection -> 7.8 cents conversion -> 7.9 note segmentation -> 7.10 ornament
#   detection -> 7.11 onset & rhythm -> 7.12 mode/raga/scale inference ->
#   7.13 assemble IR with confidences -> (section 9) adapter -> notation.
#
# ------------------------------------------------------------------------------
# 7.1 INGEST [MUST]
# ------------------------------------------------------------------------------
#   Accepted audio: wav, mp3, m4a, flac, ogg. Accepted notes: ABC, MusicXML, MIDI,
#   sargam/swara text (Carnatic/Hindustani), plain "note name" text.
#   - Validate by content sniffing, not just extension.
#   - Limits: default max 10 MB or 5 minutes for the demo (configurable); reject
#     with a clear message, never crash.
#   - Decode with ffmpeg/librosa/soundfile; mix to mono for pitch work, but keep
#     the original stereo copy for playback and stems.
#   - Resample to 16 kHz for CREPE-family models, 22.05 kHz for Basic Pitch,
#     keep a 44.1 kHz copy for separation/playback. Cache each version.
#   - Compute a content hash (SHA-256); reuse cached results for identical files.
#   - Record sample rate, channels, duration, loudness (LUFS or RMS) in IR.source.
#
# ------------------------------------------------------------------------------
# 7.2 PREPROCESS [MUST] [IMPROVE]
# ------------------------------------------------------------------------------
#   - Trim leading/trailing silence (keep a 100 ms pad).
#   - Peak/RMS normalize to a fixed target; do not clip.
#   - Optional: high-pass at ~50 Hz to remove rumble; no aggressive denoise by
#     default (it smears pitch). Make denoise opt-in [COULD].
#   - Detect clipping and very low SNR; add a warning to IR.meta.warnings.
#   - Detect if the audio is already a clean monophonic voice/instrument (low
#     polyphony score) -> skip separation (7.3) for speed.
#
# ------------------------------------------------------------------------------
# 7.3 STEM SEPARATION [SHOULD] [IMPROVE]  (prototype lacked this)
# ------------------------------------------------------------------------------
#   - Use Demucs to split vocals / other / bass / drums for songs with
#     accompaniment (pop, rock, any recording with a band or tanpura drone).
#   - Select the melody stem by: vocals stem if vocal energy above threshold,
#     else the "other" stem; allow user override ("transcribe: vocals | other").
#   - Keep the drums stem for rhythm analysis (7.11): tala/meter detection is
#     more reliable on percussion than on the melody.
#   - Separation is slow: run as a background job, show progress, cache stems.
#   - Tanpura/drone: do not subtract; USE it as a tonic cue (7.7).
#
# ------------------------------------------------------------------------------
# 7.4 MELODY ISOLATION AND THE MONOPHONIC LIMIT [MUST]
# ------------------------------------------------------------------------------
#   v1 transcribes ONE melodic line. State this in the UI. For polyphonic input:
#   (a) separate stems (7.3), (b) pick one stem, (c) run monophonic tracking on it.
#   Pop/rock: melody = lead vocal (or lead guitar via "other" stem).
#   Chords/harmony: [COULD] chord-label estimation (e.g. chroma + template
#   matching) emitted as chord symbols only; no voice-leading, no full polyphony.
#   Rap/electronic/percussion-only inputs: warn "little pitched melody found";
#   output rhythm-only result if possible.
#
# ------------------------------------------------------------------------------
# 7.5 PITCH TRACKING [MUST] [IMPROVE]
# ------------------------------------------------------------------------------
#   Prototype: simple tracker, synthetic audio only. Required:
#   - Primary: CREPE-family neural tracker (torchcrepe recommended; avoids a
#     TensorFlow dependency conflict) at 10 ms hop, with per-frame confidence.
#   - Secondary/fallback: librosa pYIN (no GPU, no model download).
#   - Basic Pitch: use for note-event proposals (audio -> MIDI-like events) and as
#     a cross-check, especially for instruments; for sung gamaka-heavy lines the
#     continuous contour from CREPE/pYIN is the source of truth.
#   - Ensemble rule: where trackers disagree by > 1 semitone (octave errors),
#     prefer the one with higher confidence and continuity; log disagreements.
#   - Octave-error correction: median filter on pitch jumps of ~1200 cents that
#     revert within a few frames.
#   - Output: frame array of (t, f0_hz|null, confidence).
#   - Config: fmin/fmax by voice type preset (male, female, instrument, auto).
#
# ------------------------------------------------------------------------------
# 7.6 VOICING CLEANUP [MUST]
# ------------------------------------------------------------------------------
#   - Drop frames below a confidence threshold (default 0.5, tunable per style).
#   - Bridge short unvoiced gaps (< 60 ms) inside a note; do NOT bridge across
#     real breaths/rests.
#   - Median-filter f0 (e.g. 5 frames) to remove spikes while preserving glides.
#
# ------------------------------------------------------------------------------
# 7.7 TONIC DETECTION [MUST] [IMPROVE]
# ------------------------------------------------------------------------------
#   Everything is relative to the tonic (Sa / root). Methods, in order:
#   1. If a drone is present (tanpura-like sustained stable partials), estimate
#      tonic from the drone's dominant stable pitch.
#   2. Otherwise build a pitch histogram in cents (folded to one octave, fine
#      bins ~10 cents, smoothed); candidate tonics = strong peaks. Score each
#      candidate by how well the rest of the histogram matches mode tables of
#      the selected style (or of all styles under auto-detect).
#   3. For Western pop/rock with key info: Krumhansl-Schmuckler-style key
#      profile as a sanity check; tonic = estimated key's root.
#   - Output top-3 tonic candidates with confidences; UI lets the user
#     override (a "Set Sa/tonic" control with an audio preview) [MUST].
#   - Wrong tonic is the most damaging error; surface its confidence prominently.
#
# ------------------------------------------------------------------------------
# 7.8 CENTS CONVERSION [MUST]
# ------------------------------------------------------------------------------
#   cents = 1200 * log2(f0 / tonic_hz), per frame; keep unfolded (octave) value
#   and the folded (0-1200) value. Do not round to note names here.
#   Reference tuning: 12-TET adapters anchor A4 = 440 Hz by default, but the
#   IR keeps the tonic in Hz so non-440 recordings are not "corrected" silently;
#   report the detected tuning offset in cents.
#
# ------------------------------------------------------------------------------
# 7.9 NOTE SEGMENTATION [MUST] [IMPROVE]
# ------------------------------------------------------------------------------
#   Prototype problem: big gamakas (> ~60 cents) split one note into two, and
#   --tolerance 120 was a stopgap. Replace with style-aware segmentation:
#   - Replace fixed tolerance with a per-style segmentation profile:
#       carnatic/hindustani/arabic : wide tolerance, merge oscillations around a
#                                    stable "anchor" pitch (gamaka-aware)
#       western_*/rock/pop         : tight tolerance (~50 cents), split on
#                                    discrete pitch steps and attack onsets
#       blues                      : medium tolerance; keep bends as ornaments
#   - Algorithm sketch: hysteresis segmentation on the contour + onset evidence
#     (energy/spectral-flux peaks). A new note starts when (a) a strong onset
#     occurs, or (b) contour moves to a different stable plateau (> style
#     threshold) for > min_duration. Oscillation around a plateau does NOT start
#     a new note.
#   - Anchor pitch per note = duration-weighted median of the plateau, not the mean.
#   - Min note length default 60 ms (per-style); shorter fragments merge into
#     neighbors or become ornaments.
#   - Expose "sensitivity" in the UI advanced panel instead of a CLI flag.
#
# ------------------------------------------------------------------------------
# 7.10 ORNAMENT (GAMAKA / MEEND / BEND) DETECTION [MUST]
# ------------------------------------------------------------------------------
#   - Per note, analyze the contour residual (contour minus anchor).
#   - Classify with explainable rules first (ML optional [COULD]):
#       oscillation (periodic, rate ~ 3-8 Hz, amplitude > 30 cents)   -> kampita-like
#       monotone glide into/out of the note                           -> slide/meend/bend
#       quick touch of a neighbor pitch                               -> grace/jaru-like
#       small constant vibrato (< ~50 cents, ~5-7 Hz)                 -> western vibrato
#   - Store measured parameters (amplitude_cents, rate_hz, direction), not just
#     a label, so adapters can approximate by rule.
#   - Naming: use tradition-specific names only when the style is explicitly set
#     and the pattern matches; otherwise use neutral names (oscillation, glide).
#     Do not claim a specific named gamaka with false certainty; report confidence.
#
# ------------------------------------------------------------------------------
# 7.11 ONSET AND RHYTHM [MUST] [IMPROVE]
# ------------------------------------------------------------------------------
#   - Onset detection: spectral flux + energy envelope; for sung legato lines
#     combine with pitch-change onsets from 7.9.
#   - Beat/pulse tracking: librosa beat tracker for pop/rock; for Indian styles,
#     estimate the base pulse (matra) from the inter-onset-interval histogram and,
#     if available, the drums/percussion stem.
#   - Cycle detection: autocorrelation / tempogram of onset strength to find the
#     repeating cycle length in pulses; score candidate cycles against the
#     style's rhythm_templates (adi 8, rupakam 3, 4/4, 3/4, 6/8, 12/8 swing, ...).
#   - Swing detection: ratio of long/short subdivisions; > ~1.4 -> swing grid.
#   - Free-time detection: if beat tracker confidence is low and IOIs are
#     irregular -> tempo.free_time = true (alapana, taksim, rubato). Render
#     unmeasured; never force bar lines.
#   - Snap onsets to the chosen grid ONLY inside adapters (section 5), and log
#     any shift larger than a tolerance as a loss item (timing_shift).
#
# ------------------------------------------------------------------------------
# 7.12 MODE / RAGA / SCALE INFERENCE [MUST]
# ------------------------------------------------------------------------------
#   - Build the note-occupancy profile: duration-weighted histogram of anchor
#     pitches in cents relative to tonic.
#   - Score candidate modes from the registry (ragas, maqams, major/minor/modes,
#     blues scale) by: coverage of used pitches, penalty for out-of-scale pitches,
#     tolerance of +/- ~30 cents (wider for gamaka-heavy styles).
#   - Return top-k candidates with scores. NEVER present a single raga as certain;
#     janya/related ragas often share the same notes. Show "closest matches".
#   - Where ragas share a pitch set, additional cues (characteristic phrases,
#     arohana/avarohana ordering) are [COULD]; state this limit in the UI.
#   - The user can pick the mode manually; manual choice overrides inference and
#     is recorded in IR.meta.
#

# ==============================================================================
# 8. STYLE AUTO-DETECT
# ==============================================================================
# Purpose: user can pick "Auto-detect" instead of choosing the input format.
#
# 8.1 Approach [MUST: heuristic scorer;  COULD: learned classifier]
#   Step 1 - Extract style features from the audio/IR:
#       - Pitch occupancy histogram in cents (fine-grained): fraction of mass
#         near 12-TET positions vs. in between (microtonal ratio).
#       - Presence of quarter-tone-like intervals (~150, ~350 cents).
#       - Ornament density and amplitude (gamaka-like oscillations).
#       - Continuity of contour (glissando proportion).
#       - Rhythm: free-time flag, cycle length, swing ratio, presence of strong
#         percussive backbeat (snare on 2 and 4), tempo.
#       - Timbre/instrument cues: voice vs. guitar vs. piano; distortion
#         (spectral flatness/centroid) as a rock cue; drone presence as an
#         Indian-classical cue.
#   Step 2 - Each adapter's score_fit(IR) returns 0..1 using its own priors
#       (e.g. carnatic: high ornament density + drone + tala-fitting cycle +
#       micro-pitch fit to swara positions).
#   Step 3 - Rank formats; return top-3 with scores.
#   Optional [COULD]: pretrained audio embedding + small classifier trained on
#   the real-recording fixtures; ensemble with heuristic scores.
#
# 8.2 Output and UX [MUST]
#   - "Detected: Carnatic (72%), Hindustani (21%), Arabic Maqam (4%)". Never a
#     bare single label.
#   - If top confidence < threshold (default 0.5) or margin between top-2 is
#     small, show "Not sure - please choose" and prefill the dropdown with the
#     top candidate.
#   - User override always wins and re-runs only the style-dependent stages
#     (tonic scoring, segmentation, ornament, mode inference), reusing cached
#     pitch tracks.
#
# 8.3 Honest limits [MUST] (show in UI help)
#   - Carnatic vs. Hindustani, or pop vs. rock, can be genuinely ambiguous from
#     a short monophonic clip. Auto-detect is a helper, not an oracle.
#   - Fusion/modern crossover music may match several styles; report that.

# 10. PART A: CHATBOT (GEMINI + ELEVENLABS)

# 10.1 Concept [MUST]
#   Each user has their own chatbot-style conversation. Gemini handles the
#   chat. ElevenLabs handles requests to create music of a given genre. The
#   user's text is first piped into Gemini to make any specifications more
#   specific, using the context of previous chats, and the resulting structured
#   request is then sent to the ElevenLabs API, producing an output file.
#
# 10.2 Per-user isolation [MUST]
#   - User accounts (hackathon-light: email/magic link or simple username + session
#     token; no passwords stored in plain text).
#   - Each user has: their own chat threads, memory/preferences, generated tracks,
#     and Library. No cross-user reads; enforce on every query by user_id.
#   - Threads: create, rename, delete, list. Messages stored with role, text,

#
# 10.3 Message flow (granular) [MUST]
#   1. User sends text (optionally attaches a Library track or selects a genre
#      chip from the registry).
#   2. Backend loads context: last N messages (token-budgeted), user preferences
#      (favorite genres, instruments, skill level, language), and previously
#      generated track specs from this thread.

#        - "generate"    : create music                            -> goto 4
#        - "transcribe"  : user wants notation for an attached track -> hand off to

#   4. Spec refinement (Gemini): take the user's request + context and output a
#      STRICT JSON music spec (10.4). Gemini fills reasonable defaults from prior
#      turns ("same mood as the last one, but faster") and lists assumptions.

#      duration within limits, no disallowed content (10.7). On failure, one

#   6. Show the user a compact "Here's what I'll make" confirmation chip row
#      (genre, tempo, mood, duration, instruments) with Edit / Generate buttons.
#      [SHOULD: auto-generate without confirmation under a toggle]
#   7. Convert spec -> ElevenLabs request: compose a descriptive prompt string
#      (and, if the API supports it, a structured composition plan with sections /
#      mid-track genre transitions) from the JSON spec.
#   8. Call ElevenLabs Music API as a background job; stream status to the chat
#      ("Composing...").

#      audio player, waveform, download, and action buttons (Open in Workspace,

#      reproducibility and the "How was this made?" panel.

#   7. Workspace (Part C) minimum credible demo (12.10) + integrations.
#   8. Style auto-detect heuristic, then polish, accessibility, demo rehearsal.
#
# 14.2 Demo script (target ~3 minutes)
#   1. In Chat: "Make a short Carnatic alapana that turns into jazz piano."
#      Gemini refines -> ElevenLabs generates -> player appears.
#   2. "Transcribe this" -> Notation Studio: Auto-detect says Carnatic; output =
#      Western staff. Show sargam AND staff.
#   3. Loss report: gamaka dropped, microtone rounded; Gemini explains; ElevenLabs
#      narrates.
#   4. "Open in Workspace": MIDI clip in the piano roll, layer a drum step pattern,
#      export WAV.
#   Message to judges: transcription is approximate by design; the loss report
#   is the teaching tool.
#
# 14.3 Judging-criteria mapping
#   Education track : loss report + explanations + glossary + accessibility.
#   ElevenLabs prize: Music API (generation, fusion/transitions), TTS narration.
#   Gemini prize    : conversational context, spec refinement, loss explanation.
#
# 14.4 Key risks and mitigations
#   R1 Real-audio accuracy is lower than synthetic.   -> real fixtures early; show confidence; tonic override.
#   R2 Raga/maqam/tala tables are wrong.              -> practitioner review; review badges; hedge language.
#   R3 ElevenLabs music needs a paid plan / API drift. -> detect, fallback stand-in, verify docs pre-demo.
#   R4 Gemini model names change.                      -> env-configured model; test before demo.
#   R5 Part C scope explosion.                         -> 12.10 minimum demo; cut effects/automation.
#   R6 Generated music does not match a transcribed melody. -> label as "inspired by"; use MIDI for fidelity.
#   R7 Compute time (Demucs/CREPE).                    -> caching, progress UI, skip separation when clean.
#   R8 Copyright/artist-name prompts.                  -> sanitization (10.7).
#   R9 Overclaiming ("supports everything").           -> explicit supported list + extensible architecture.
